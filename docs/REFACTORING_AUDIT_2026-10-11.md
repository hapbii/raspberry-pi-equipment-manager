## 추가 수정

| 파일 | 변경 이유와 결과 |
|---|---|
| `vision/detector.py` | predictor의 첫 이미지 속성 정리가 중단되면 나머지 이미지 속성은 해제되지 않았습니다. 모든 속성 정리를 시도한 후 최초 중단 예외를 전달합니다. 종료·초기화 실패에서는 이미지 정리가 중단돼도 모델에서 predictor를 분리하며, 정리 traceback의 모델·predictor 지역 참조도 해제합니다. |
| `vision/service.py` | 인식 후 상태 정보 처리에 실패하면 완료된 인식 프레임이 detector를 붙잡았습니다. 인식·사전 점검·종료의 오류 경계에서 완료된 traceback 프레임을 해제하고, 사전 점검의 detector 지역 참조도 제거합니다. 인식 잠금 해제와 기존 성공·실패 집계 동작은 유지합니다. |
| `hardware.py` | GPIO 장치 생성이나 worker 시작에 실패하면 종료한 장치와 부분 생성된 표시기가 생성자 traceback에 남았습니다. 생성·시작·실패 정리를 하나의 흐름으로 모으고, 오류 프레임과 부분 인스턴스 참조를 해제합니다. 일부 장치만 생성된 경우와 전체 장치를 생성한 경우의 정리 소유권을 구분합니다. |
| `__init__.py` | 앱 생성 중 DB 초기화 등이 실패하면 반환되지 않은 앱과 종료한 서비스가 traceback에 남았습니다. 실패 시 모든 서비스를 정리한 뒤 앱·로그 저장소·heartbeat 지역 참조 및 종료 콜백의 앱 참조를 해제합니다. 서비스 종료 오류도 기록 전에 완료된 프레임을 해제합니다. |

공통 `release_error_frames()`를 사용하므로 traceback의 파일·행·예외 메시지와 원인 연결은 유지됩니다. 실행 중인 프레임은 지우지 않습니다. 정상 운영 중 모델을 매번 새로 로딩하거나 인식 기준을 낮추는 변경은 없습니다.

## 오류 재현과 회귀 검사

새 `tests/test_failure_resources.py`의 5개 검사는 수정 전 모두 실패했고, 수정 후 통과했습니다. GPIO 생성/worker 시작의 두 하위 조건까지 포함하면 수정 전 실패 조건은 6개입니다. 예외 객체를 계속 보관하면서 약한 참조로 객체 해제를 확인합니다.

- 이미지 속성 정리 중단 100회: 카메라 크기의 합성 버퍼 400개 해제.
- 이미지 정리가 중단된 종료 100회: 모델이 살아 있어도 predictor 100개 분리·해제.
- 상태 정보 처리 실패 100회: 종료한 detector 100개 해제, 인식 잠금 정상 해제.
- GPIO 부분 생성 실패·worker 시작 실패 각 20회: 생성한 장치 80개 모두 종료·해제.
- 앱 시작 실패 20회: 앱 20개와 종료한 서비스 20개 해제, 로그 핸들러 복원.

오류 주입에는 모의 장치와 합성 버퍼를 사용했으며 실제 GPIO·카메라 드라이버 검사는 아닙니다.
